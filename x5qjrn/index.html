What this note covers

The previous lab note, “Standing up the NetBird controller: the VM, the ports, the DNS record, and hardening Ubuntu,” left the mesh fail-closed right after the first login: the Default policy was gone, and no peer could reach any other peer yet because nothing had been enrolled or granted anything. This note covers the rest of the access-control model - why peers reach each other directly instead of through a routing gateway, what groups and policies actually do, the order to build them in, enrolling the Windows/Timon host and the iPhone as real peers, and scoping a private DNS zone to only the people who need it.

Peer-to-peer, not routing-peer

NetBird offers two distinct ways to reach a device:

ModelHow it works
Direct peer-to-peerThe target device itself runs the NetBird client and becomes a full mesh peer - reachable directly (or via relay/STUN if direct UDP fails), with its own identity, groups, and policies
Networks / routing-peer modelUsed for devices that can't run a NetBird client (embedded devices, IoT, legacy boxes) - another peer on the same LAN acts as a routing gateway, advertising a Resource (an IP/CIDR/domain) on their behalf. Traffic is routed through that gateway peer rather than reaching the target's own WireGuard identity directly

Why direct peer-to-peer was chosen for bigdude (the Timon host) and the home-automation hub:

  • Both can run a full NetBird client directly - no embedded or legacy constraint forcing the routing-peer workaround.
  • Smaller trust surface. A routing peer becomes a single chokepoint that can see/relay traffic for every resource behind it; direct P2P means each device enforces its own policy independently, with no intermediary peer to compromise.
  • Simpler policy model. P2P groups/policies target the device itself - one group membership, one set of rules. The Networks model adds an extra layer (resource definition, routing-peer assignment, and a policy on the resource) for no benefit here, since there's no non-client-capable device requiring it.
  • No extra hop. Direct (or relay-assisted) P2P is one WireGuard hop; routing-peer traffic adds a second hop through the gateway peer's LAN.

When the routing-peer model would be the right call instead: a smart-home device that truly cannot install a NetBird client (a sensor, a proprietary hub with no package support). Then a single /32 Resource pointed at just that device's LAN IP, routed through one trusted gateway peer and scoped to the narrowest possible policy, is the appropriate tool - reserved for that case only, not used as the default.

Groups, policies, and the Default policy

Three concepts explain how NetBird access control works end to end:

ConceptWhat it means
GroupsNamed sets of peers (and optionally resources), similar to tags. A peer can belong to multiple groups. A built-in All group auto-contains every peer - it cannot be deleted or renamed
PoliciesALLOW rules only - no explicit deny/priority system. A connection is permitted only if some policy's Source/Destination groups match both ends; everything else is denied by default. Each policy is bidirectional or unidirectional (only the source side can initiate)
Default policyAuto-created on account creation, using All → All, bidirectional - i.e. full mesh, everyone can reach everyone. Intentionally permissive to make initial setup painless

Official reference: Managing Access with NetBird: Groups and Access Policies.

Building groups and policies in the right order

  1. Enroll first. Add the core devices as peers before touching policies - bigdude (Timon host), the home-automation hub, and the iPhone. With the Default policy still active they can all already reach each other, which is fine for initial verification.
  2. Create custom groups, e.g. timon-hosts (any machine running Timon), hub (the home-automation hub), iphone (the personal phone), and timon-admins (devices allowed to browse/administer Timon remotely - likely just iphone plus any other personal device).
  3. Delete (or disable) the Default All→All policy once the core devices are enrolled and grouped - do this before adding any further or future device, so nothing new is implicitly granted full access.
  4. Create narrow policies, one per real need, e.g. iphone → timon-hosts on TCP 443 only, unidirectional (the phone initiates, the host doesn't need to reach back), and iphone → hub on whatever port(s) the hub's own UI/API needs, also unidirectional. Avoid any All-group policy going forward - always name explicit source/destination groups.
  5. Scope any private DNS name (Custom Zone) to the specific Distribution Group that needs it (e.g. timon-admins), never to All.

Why this order, not groups-then-policies-then-enroll: enrolling first while the Default policy is still active keeps initial verification simple - every peer can reach every other peer while confirming the client install itself works, before any policy logic is in play. Deleting the Default policy only after enrollment, but strictly before any future device joins, closes the exposure window without blocking the setup work in progress.

A natural next hardening step: the policies above control which groups can reach each other, but NetBird can also condition access on the state of the connecting device via Posture Checks - e.g. requiring a minimum NetBird client version, restricting by country/region, allow/deny-listing peer network ranges, requiring specific running processes, or an OS-issued certificate. Attaching a posture check to the iphone → timon-hosts policy (for example, a minimum client version) is a reasonable follow-up once the base groups/policies above are working - not done in this pass.

Enrolling the Windows/Timon host

  1. Download the NetBird EXE or MSI installer from https://pkgs.netbird.io/windows/x64 (or /windows/msi/x64). Official docs: docs.netbird.io/get-started/install/windows.
  2. Run it - installs to C:\Program Files\NetBird and registers the NetBird daemon as its own Windows service automatically.
  3. Open a new terminal (PATH only updates for new terminals):PowerShell
    netbird up --management-url https://netbird.mydomain.cloud
    Follow the browser SSO link to authorize the peer. If the device code expires (a few minutes), re-run netbird down then netbird up ... again to get a fresh one.
  4. Confirm the assigned private IP:PowerShell
    netbird status
    Example used throughout for the bigdude machine: NetBird IP 100.64.108.163.
  5. In the NetBird Dashboard, add this peer to the timon-hosts group created earlier in this note.
  6. Test reachability over cellular (Wi-Fi off, NetBird toggled on in the app): browse to https://bigdude.mydomain.cloud - should load Timon's sign-in page exactly as from a laptop on the mesh. (The reverse proxy serving that page is set up in the next lab note, covering making Timon and Windows reachable - the mesh reachability tested here is independent of it.)

Enrolling the iPhone

  1. Install NetBird from the App Store (official app, published by netbird.io).
  2. Open the app → tap Add Profile (or the equivalent first-run prompt) → enter the management URL: https://netbird.mydomain.cloud (same self-hosted controller as the Windows peer).
  3. Tap Connect / Sign in - this opens the same browser-based SSO login used for every other peer. Log in with the NetBird account and approve the authorization request.
  4. iOS shows a system prompt to Add VPN Configurations - tap Allow (iOS implements NetBird's WireGuard tunnel as a standard VPN profile; this is expected and required for the tunnel to work).
  5. Once connected, the app shows Connected with the phone's assigned NetBird IP - confirm it in the NetBird Dashboard's Peers list as well.
  6. In the NetBird Dashboard, add this peer to the iphone group created earlier in this note - this is what the iphone → timon-hosts / iphone → hub policies target.
  7. Test reachability over cellular (Wi-Fi off, NetBird toggled on in the app): browse to https://bigdude.mydomain.cloud - should load Timon's sign-in page exactly as from a laptop on the mesh.

The Custom DNS Zone

Create the zone, add the hosts, and scope distribution - the steps followed in this setup:

  1. NetBird Dashboard → DNS → Nameservers/Zones (naming varies by dashboard version) → Add Zone.
  2. Zone name/domain: the base domain used for every entry in this zone, e.g. mydomain.cloud - must match the OVH-hosted domain used for the controller's own DNS record.
  3. Add Record, one per hostname, target set to the peer's NetBird IP (found via netbird status on that machine, or the Dashboard's Peers list):
    HostnameTargetPurpose
    bigdude.mydomain.cloudbigdude's NetBird IP, e.g. 100.64.108.163Web UI (human browsing)
    bigdude-daemon.mydomain.cloudsame NetBird IP - same peer, different reverse-proxy site blockDaemon API (device pairing / Machines plugin)
  4. Distribution group(s): on the zone (or per record, depending on dashboard version), set this to timon-admins - never All. Only peers whose group is listed here receive this DNS record at all; everyone else gets no resolution for it, by design.
  5. Save, then from an already-enrolled peer in that distribution group, confirm resolution: nslookup bigdude.mydomain.cloud (or ping) should return the expected NetBird IP within a minute or two of saving.
  6. Whenever a group is renamed or restructured (splitting a group, adding new admin devices), revisit this zone's distribution group list - it does not update automatically, and a stale list silently breaks resolution only for the newly affected peers (see the troubleshooting note below).

Both hostnames reuse the same OVH DNS-01 credentials - the reverse proxy set up in the next lab note requests and renews a separate certificate per hostname automatically. Confirmed working end to end: the reverse proxy's logs show challenge_type: dns-01, authz_status: valid, and certificate obtained successfully for bigdude.mydomain.cloud with no errors (first-run "cannot find path" messages are benign - just the proxy creating its local ACME account file).

TLS summary: browser/iPhone ↔ reverse proxy is HTTPS with a real, publicly-trusted Let's Encrypt certificate (no warnings); reverse proxy ↔ Timon (127.0.0.1:3110 / 127.0.0.1:3010) is plain HTTP over loopback only, which never leaves the machine.

Troubleshooting ERR_NAME_NOT_RESOLVED on the custom zone hostname: unlike the automatic per-peer name, a Custom Zone record is only pushed to peers whose group is listed in that zone entry's Distribution group field - it is not a mesh-wide DNS record. If a peer (e.g. the iPhone) can resolve its own automatic peer name but gets ERR_NAME_NOT_RESOLVED specifically on bigdude.mydomain.cloud, the fix is: NetBird Dashboard → DNS → Zones → the zone entry → confirm the peer's actual group (e.g. Admins) is listed under Distribution group - not just the group(s) the zone was originally scoped to. A group rename or restructuring can leave the zone's distribution list stale, silently breaking resolution for the affected peer only (toggling the NetBird connection off/on forces a fresh config pull once the group is fixed).

Official reference: DNS in NetBird (Nameservers, Custom Zones, Match/Search Domains).
