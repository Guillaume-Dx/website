The DNS record

In the OVH DNS zone for mydomain.cloud, add an A record netbird → the Freebox's public IP. Since the Freebox's WAN IP can change (unless a fixed-IP option is in place), two options:

  • Use the Freebox's built-in DynDNS setting pointed at Free's own hostname, then add a CNAME netbird.mydomain.cloud → that Free hostname in OVH.
  • Or manually update the OVH A record, if the IP changes rarely in practice.
TypeNameContentNotes
AnetbirdFreebox public IP (or DynDNS target)must already exist before running the quickstart script
CNAME*.netbirdnetbird.mydomain.cloudonly needed if the optional NetBird Proxy service is enabled

Set this up first: DNS propagation can take time, and the base A record must exist before running the quickstart script, further down in this note - it's how the script's own ACME/Let's Encrypt validation finds the controller.

What the controller needs

The official requirements for the self-hosted controller, kept deliberately modest:

RequirementDetail
VM sizingLinux VM, 1 vCPU / 2GB RAM minimum
Public reachabilityTCP 80 and 443, plus UDP 3478 (STUN/relay)
Public domainMust resolve to the VM's public IP - here, netbird.mydomain.cloud (OVH-hosted zone)

Creating the VM on the Freebox

  1. Freebox OS → VM section → create a new VM. Ubuntu Server (latest LTS), 1+ vCPU, 2GB+ RAM, a dedicated disk (10-20GB is plenty for a management server, signal server, relay, and dashboard - none of them store much data).
  2. Give the VM a static DHCP lease on the Freebox. Without it, the VM's LAN IP could change on a lease renewal or reboot, silently breaking the port-forwarding rules set up next in this note - they target a fixed LAN IP, not the VM by name.

Port-forwarding, and the CGNAT check

Freebox OS → Port forwarding, targeting the VM's static LAN IP:

WAN portProtocolPurpose
80TCPACME HTTP-01 / redirect
443TCPDashboard, API, Proxy (Traefik)
3478UDPSTUN/relay

Verify the Freebox is not behind CGNAT first. Compare the Freebox's reported WAN IP to what an external "what's my IP" check reports, checked from outside the home network. If they differ, the ISP is NAT-ing the Freebox itself behind a shared public IP (Carrier-Grade NAT) - in that case the port-forwarding rules above are meaningless, since the Freebox's own public-facing address isn't actually public, and a different reachability strategy is needed before going any further.

Hardening Ubuntu: updates, SSH, firewall

Automatic security updates - important since this VM is directly internet-facing:

Ubuntu - unattended upgrades
sudo apt install unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades

SSH hardening. Disable password auth, key-based only (PasswordAuthentication no in /etc/ssh/sshd_config), consider changing the default port or at minimum fail2ban/rate-limiting if left on 22. SSH is never port-forwarded on the Freebox (covered earlier in this note), so the remaining gap is any device already on the LAN being able to reach it, not just admin devices - closed at the ufw level below, by restricting SSH to the LAN subnet. Once the mesh is actually up, SSH can additionally be restricted to only be reachable over NetBird itself - left as a chicken-and-egg problem for now: the Freebox VM console stays the out-of-band fallback for this very first setup, before NetBird exists to tunnel through.

Firewall (ufw) - default-deny inbound, explicitly allow only what's needed:

Ubuntu - ufw rules
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp   # SSH, LAN-only - replace with your actual LAN subnet (check with `ip addr`)
sudo ufw allow 80/tcp      # ACME HTTP-01 / redirect
sudo ufw allow 443/tcp     # Dashboard, API, Proxy (Traefik)
sudo ufw allow 3478/udp    # STUN/relay
sudo ufw enable

Verify with sudo ufw status numbered: the SSH rule should show the subnet, not Anywhere. Optionally narrow further to a single admin IP, e.g. sudo ufw allow from 192.168.1.50 to any port 22 proto tcp. Test from a device outside the LAN (e.g. phone on cellular, NetBird disconnected) that ssh to the controller's LAN IP now times out/refuses, while a LAN device still connects.

Preparing for NetBird: Docker, time, swap, backups

Docker install - the self-hosting quickstart script needs Docker + the Compose plugin, plus jq and curl as utility dependencies:

Ubuntu - Docker and utilities
sudo apt install -y docker.io docker-compose-plugin
sudo apt install -y jq curl

Time sync - ensure systemd-timesyncd (default on Ubuntu) is active. Accurate clocks matter for TLS certificate validity and ACME, and more generally for any token/code expiry checks across the mesh.

Swap (optional but sensible on a 2GB VM) - a small swapfile as a safety margin for the Docker stack under memory pressure:

Ubuntu - swapfile
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

Backups. Back up the generated config.yaml, docker-compose.yml, dashboard.env/proxy.env, and the Docker volumes - this is the entire NetBird account database (users, peers, groups, policies). This VM is the single source of truth for the whole mesh's identity and access control once set up, so losing it without a backup means rebuilding every peer and policy from scratch.

NetBird quickstart script

After hardening Ubuntu (previous step in this note), download and run NetBird's official self-hosting installer (copy the exact current command from the live docs page at install time - it is versioned and changes): docs.netbird.io/selfhosted/selfhosted-quickstart.

Choices the script asks for:

  • Reverse proxy selection. Chose option [0] (Traefik) - bundled, handles Let's Encrypt automatically, zero extra config. Not to be confused with the Caddy reverse proxy used later for Timon itself, covered in a later lab note - that one runs on each Windows machine, not on the NetBird controller.
  • NetBird Proxy service (optional). Exposes per-service subdomains (*.netbird.mydomain.cloud) - if enabled, the wildcard CNAME DNS entry set up earlier in this note must already be in place.
  • CrowdSec (optional). Offered alongside the proxy for community IP-reputation blocking - worth enabling for a controller exposed to the public internet.

Why the Default policy must be disabled immediately, not "left and restricted later". The Default policy (All → All, bidirectional) makes the mesh fail open: every peer that joins can already reach every other peer, with no explicit decision made for that pairing.

OptionShort-term costConsequence
(a) Leave Default active, add stricter policies laterConvenient short-termEvery device enrolled in the meantime (test device, guest's phone during troubleshooting) is immediately and fully exposed to every other peer, with no review step and no grace window - exposure starts the instant a peer authorizes
(b) Delete/disable Default immediately after enrolling the core devicesA few groups + narrow policies up front, covered in the next lab noteThe network fails closed from that point on: a newly joined peer has zero reachability until a human deliberately writes a policy granting it something - deferred hardening is a common source of forgotten exposure, since there's rarely a forcing function to go back and do it once things "just work"

Decision: (b). The Default policy was deleted right after the first three devices (bigdude, the hub, the iPhone) were grouped, and before any further peer was added to the account. Going forward, every new peer requires an explicit group assignment and policy before it can reach anything, by construction.

Generated files: docker-compose.yml, config.yaml, dashboard.env, and (if the proxy is enabled) proxy.env. Manage the stack afterwards with docker compose commands from that directory.

First login

  1. Browse to https://netbird.mydomain.cloud - redirects to /setup (only reachable while no users exist yet).
  2. Create the admin account: email, name, password.
  3. Log in normally afterwards.
