Three weeks, eleven projects: what actually ran on its own

Oct 23, 2026 Multi-project portfolio · Kanban pipelines · Concurrent missions · Self-healing agents

On this page

  1. What got built
  2. How it ran
  3. Keeping itself on the rails
  4. What this adds up to

What got built

Over the last three weeks I stopped feeding Timon one project at a time and let it loose on eleven of them at once: a small invoicing app, a stock-tracking analyst, Timon's own plugin platform, and eight others running in parallel. I didn't sit over any of them full-time. Most of them didn't ask me to.

  • An invoicing app for a care professional. I had it build a model-driven app that logs client sessions and turns each one into a PDF invoice, sized by session type and length, routed to the professional for a look before it ever reaches the customer. It built the thing, reviewed its own work, fixed what needed fixing, and only stopped me once: a single blocked task where it genuinely needed my call instead of guessing.
  • A home-automation hub and dashboard. This one started from an empty repository and grew into a working integration across two home-automation protocols, shipped in steady version bumps. At one point it wasn't sure whether its agents were allowed to touch another project's work, so it stopped and asked me instead of assuming.
  • A stock-tracking analyst. I described the idea in a single sentence and watched a team of six agents, an orchestrator, an analyst, a coder, a reviewer, a writer, assemble itself, wire in a daily scheduled run, and bring me the open questions, a missing second price source, an ambiguous ticker, as explicit choices instead of silent guesses.
  • A platform migration for the professional project I audited in my first lab note. Four stages to retire a legacy component, each one a dependent task that only started once the previous one had actually closed. No skipping ahead.
  • A personal knowledge base. Turning a pile of voice notes, transcribed to markdown, into a structured set of notes I can actually explore and connect.
  • A companion device app. This one hit an open research question mid-build. Rather than guess at an answer, it paused and waited for a real one before picking the build back up.
  • An onboarding tour and an onboarding wizard plugin. One teaches newcomers how Timon works, the other automates setting up a brand-new project, objectives, roadmap, agent team, Kanban seeding, in one pass, so the next project I start will move faster than this one did.
  • Timon's own plugin platform. Started from a folder that was genuinely empty, not even a git repo. It created the repository, shipped a first plugin, then several more in parallel, one of them held back behind a go or no-go call I made myself before it shipped.
  • A small API module for an existing platform. This one was thinner: a single scoped coding task, a set of data-contract classes for an existing platform's API. No team assembled, no back and forth, just a clean, bounded piece of work done and merged.
  • This website. The one hosting this very note, kept current as the other ten evolve.

How it ran

Each project lives on its own Kanban board. Tasks are typed, code, research, doc, chore, review, merge, and chained through dependencies, so a merge task only fires once everything it depends on has closed. I watched work move from code to review to merge without ever pushing it forward myself. Across the eleven projects, over a thousand tasks closed that way in three weeks.

A few boards ran concurrent missions on the same afternoon: separate agents working the invoicing app, the home hub and the plugin platform at once, each in its own worktree so one project's work never blocked another's. Scheduling showed up as recurring workflows, the analyst's daily run among them, firing themselves on a clock instead of waiting on me. Prioritization showed up as blocked tasks with an explicit reason attached, sitting there until I made a call, never silently dropped or guessed at.

Keeping itself on the rails

A good part of what made this scale possible wasn't the code the agents wrote, it was how much of their own trouble they sorted out without me. One agent got assigned a model its provider no longer supported and started crash-looping, I found the fix already diagnosed and swapped in, I only had to confirm it. A plugin threw an export error after an update, traced to a stale cached module inside the daemon, cleared by disabling and re-enabling it. A corrupted local lock file kept crashing a mission on every retry, it got narrowed down to two exact files, I only had to delete them. One agent tried to create a project folder in a protected location, and instead of just failing, it escalated the request to an admin-level agent rather than give up.

Each of these would have cost me an afternoon of log-reading on my own. Here, it cost me a few minutes: read a clear diagnosis, approve a fix.

What this adds up to

Eleven projects moved forward and more than a thousand tasks closed in three weeks, and I never had to babysit any single one of them. The lesson isn't that the agents can code, it's that the same framework can run many unrelated efforts at once, each at its own pace, bring me only the handful of decisions that genuinely need me, and quietly fix most of what breaks along the way before I even notice.
