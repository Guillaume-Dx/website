What this note covers

The previous lab note, “Making Timon and Windows reachable: Caddy, DNS-01, and the app/daemon split,” closed the last piece of the build: a reverse proxy in front of Timon, a CA-trusted certificate, and two hostnames that never get confused. Every individual decision in this series - the self-hosted controller, groups and policies instead of a flat mesh, the Custom DNS Zone, Caddy - now needs to be seen as one picture instead of six separate ones.

This closing note is that picture: the full architecture end to end, then the exact mechanics of why a laptop on a café network can reach bigdude sitting behind a home router that blocks every unsolicited inbound connection it receives.

Reading the diagram:

  • Step 1, thin arrows, to the controller: every mesh peer - laptop, iPhone, bigdude, the hub - authenticates to the self-hosted NetBird controller VM on the Freebox via SSO, and receives the current peer list, routes, and access policy from it. The controller never sits in the actual data path once peers know how to reach each other.
  • Step 2, thick/dashed arrows, peer-to-peer: actual traffic between an external device and a LAN peer flows as a direct WireGuard tunnel between the two peers, NAT-traversed, only relayed through the controller's relay/TURN component as a fallback when direct UDP fails - this is the peer-to-peer model chosen over a routing-gateway model.
  • Green box, onboarded: bigdude and the hub run the NetBird client themselves, so they're reachable individually, each governed by its own group and policy - nothing is reachable by default.
  • Orange box, not onboarded: any LAN device without a NetBird client (NAS, printer, legacy IoT) is only reachable from other devices already on the LAN - remote peers have no path to them at all unless a routing peer is deliberately configured for that specific device, which this build does not do by default.
  • The Freebox itself only does port-forwarding (80/443/3478) to the controller VM - it is not in the data path for peer-to-peer traffic once peers have connected directly.

Why the Freebox blocking inbound traffic doesn't stop any of this

The Freebox blocks unsolicited incoming traffic by default, and nothing in this build changes that. The WireGuard tunnel still forms, because of how NAT traversal (UDP hole punching) works: the connection is always initiated from inside the LAN outward, never accepted as an unsolicited inbound connection.

  1. The LAN device dials out first. bigdude (or the hub), running the NetBird client, opens an outbound UDP connection to the controller/signal server. The Freebox's NAT/firewall always allows outbound traffic and the return replies on that same connection - this is normal, expected NAT behavior, not a port-forward.
  2. The signal server introduces both sides. The external laptop or phone also connects outbound to the controller. The controller, via its signal component, exchanges each side's public IP:port (as seen from the outside, after NAT) and WireGuard public keys - it's matchmaking, not routing the data.
  3. Hole punching. Both peers then send UDP packets toward the other's observed public address, simultaneously, from the connections they already have open outbound. Because the Freebox's NAT table now has an “expected return traffic” mapping for that external address:port, the incoming WireGuard packets from the external peer are seen by the Freebox as replies to a connection it opened itself - so they're let through, with no port-forward rule needed at all.
  4. If hole punching fails (strict/symmetric NAT, some mobile carriers), NetBird falls back to the relay/TURN component - which both sides are already connected to outbound, so again no inbound port is needed; traffic is relayed through a connection both sides initiated.

So the only port-forward actually configured on the Freebox (80/443/3478) is for the controller VM itself to be reachable - dashboard, ACME, STUN - not for bigdude or the hub. Those LAN devices are reached purely via connections they themselves opened outward, which is exactly why no incoming-traffic rule is needed for them specifically.

Key takeaway: the controller is only ever involved in steps 1-2 - authenticate, authorize, exchange addresses. From step 3 onward, the controller either steps out of the path entirely (direct P2P) or stays only as a passive relay (fallback) - it never initiates or accepts an inbound connection to the LAN on bigdude's behalf, which is why no Freebox port-forward is required for bigdude itself.

What this series actually proves

Six notes to get here, and the architecture diagram above is the whole point condensed into one picture: self-host the control plane, trust nothing by default, and never expose a raw port to the internet - yet still reach a home machine from anywhere, over a direct encrypted tunnel, without a single inbound firewall rule on the devices that matter. The Freebox never has to let anything in; the LAN devices always dial out first, and that one property is what makes the rest of this build safe to leave running unattended.
