What this note covers, and Timon's non-negotiables

The previous lab note, “Groups and access policies: enrolling bigdude and the iPhone,” left bigdude and the iPhone enrolled, grouped, and scoped by narrow policies. This note covers the last piece: making Timon itself reachable over the mesh and from Windows - the non-negotiables, the reverse proxy, the certificate automation behind it, and why the web app and the daemon need two separate hostnames.

Five rules apply throughout, non-negotiable because getting any of them wrong either breaks pairing or exposes Timon directly to the internet:

RuleDetail
Loopback onlyTimon's two listeners - web app (app.listen, default 127.0.0.1:3100) and daemon API (daemon.listen, default 127.0.0.1:3000) - stay on 127.0.0.1 forever. Never bind to 0.0.0.0 or a network interface IP directly
Admin account firstCreate the administrator account (local access or SSH tunnel) before opening anything else to the mesh
behindTlsProxyOnce a reverse proxy sits in front, set daemon.behindTlsProxy: true and restart
Auth stays onNever set daemon.auth to "off"
No automatic HTTPSUnlike Tailscale's tailscale serve, NetBird has no built-in HTTPS - a manual reverse proxy (Caddy) with a real certificate is required

Windows background-run notes

  • Timon runs via the TimonOrchestrator scheduled task (not a true service), started at boot and surviving sign-out - but waiting for the first sign-in after every restart. For an always-reachable machine: enable automatic sign-in (netplwiz → uncheck “Users must enter a user name and password”), or sign in manually after each reboot. Also disable sleep: Settings → System → Power → “When plugged in, put my device to sleep after” → Never - a sleeping machine answers nothing, scheduled task or not.
  • Config file: %USERPROFILE%\.timon\timon.config.json.
  • Service control: timon service status / timon service stop / timon service start.
  • Health/restart events, port status, and startup warnings show in the desktop log (%USERPROFILE%\.timon\tmp\daemon-<date>.log) - a “did not answer within 120s” or ERR_CONNECTION_REFUSED warning simply means the daemon/app hadn't finished starting yet. Wait for the health check to report OK before troubleshooting further - it can take up to ~180s after a service restart, and chasing the warning as if it were a real failure wastes time on a condition that resolves itself.

Keeping Timon's listeners on loopback

Confirm in %USERPROFILE%\.timon\timon.config.json (actual values on bigdude: app on 3110, daemon on 3010 - non-default ports, confirm against your own install):

timon.config.json
{
  "app": { "listen": { "host": "127.0.0.1", "port": 3110 } },
  "daemon": { "listen": { "host": "127.0.0.1", "port": 3010 }, "behindTlsProxy": true }
}

OVH API credentials for DNS-01

The caddy-dns/ovh plugin needs four values: an endpoint name and three secrets (application key, application secret, consumer key).

These credentials are scoped to the OVH zone/account, not to any one machine. The same application_key/application_secret/consumer_key can (and should, for simplicity) be reused in every machine's Caddyfile dns ovh block - what they authorize is “permission to edit DNS records in this zone,” which any Caddy instance needs regardless of which machine it runs on. Each machine still gets its own certificate for its own hostname; only the credential is shared. A separate token per machine is optional, only useful for easier per-machine revocation later. If a machine's Caddyfile is missing these values (or has placeholders), Caddy's log shows missing authentication information, you need to provide one of the following: application_key/application_secret, client_id/client_secret, or access_token - that error means the credentials below were never actually set on that machine.

  1. Go to OVH's API credential creation page for your account's region - for most European .cloud/.com domains managed under the EU dashboard, this is https://eu.api.ovh.com/createToken/ (use ca.api.ovh.com or us.api.ovh.com instead if the OVH account is Canada/US-based - this also determines the endpoint value in the Caddyfile: ovh-eu, ovh-ca, or ovh-us).
  2. Fill in: Application name (e.g. caddy-dns-mydomain), Application description (e.g. Caddy DNS-01 for mydomain.cloud), Validity (unlimited, or set a renewal reminder to time-box it).
  3. Grant exactly these API rights, scoped to the zone (replace mydomain.cloud with the real domain - narrower is better than the wildcard * scope):OVH API rights
    GET    /domain/zone/mydomain.cloud/record
POST   /domain/zone/mydomain.cloud/record
GET    /domain/zone/mydomain.cloud/record/*
PUT    /domain/zone/mydomain.cloud/record/*
DELETE /domain/zone/mydomain.cloud/record/*
GET    /domain/zone/mydomain.cloud/soa
POST   /domain/zone/mydomain.cloud/refresh
  4. Submit - OVH immediately returns an Application Key and Application Secret. Save both now; the secret is shown only once. Generating the Consumer Key (binds the application key to the account with the rights above) requires one authenticated call to OVH's API - the create-token web form above typically already returns all three values together; if using the raw API flow instead, use ovh/go-ovh's helper or OVH's own “Create consumer key” quickstart with the same endpoint and application key.
  5. Store all three values (application_key, application_secret, consumer_key) plus the endpoint (ovh-eu) securely - e.g. as Windows environment variables referenced from the Caddyfile instead of hardcoding them in plaintext:PowerShell
    [System.Environment]::SetEnvironmentVariable("OVH_ENDPOINT", "ovh-eu", "Machine")
[System.Environment]::SetEnvironmentVariable("OVH_APPLICATION_KEY", "...", "Machine")
[System.Environment]::SetEnvironmentVariable("OVH_APPLICATION_SECRET", "...", "Machine")
[System.Environment]::SetEnvironmentVariable("OVH_CONSUMER_KEY", "...", "Machine")

The variables are referenced in the Caddyfile with {$OVH_ENDPOINT}, {$OVH_APPLICATION_KEY}, etc. instead of inline strings - keeps secrets out of the Caddyfile itself (restart the Caddy service after setting machine-level env vars so it picks them up).

Building a custom Caddy with xcaddy

Stock Caddy binaries (from caddyserver.com/download) don't include third-party DNS provider plugins like caddy-dns/ovh - they must be compiled in via xcaddy. This is built directly on the Windows machine, in PowerShell, with no Linux/WSL step needed.

  1. Install Go for Windows (one-time): download and run the installer from go.dev/dl (pick the .msi for windows-amd64), then open a new PowerShell window so PATH picks up go.exe. Confirm:PowerShell
    go version
  2. Install xcaddy:PowerShell
    go install github.com/caddyserver/xcaddy/cmd/xcaddy@latest
$env:PATH += ";$(go env GOPATH)\bin"
    Add $(go env GOPATH)\bin to the permanent PATH via System Properties → Environment Variables, so this doesn't need repeating in every new session.
  3. Build caddy.exe with the OVH plugin:PowerShell
    xcaddy build --with github.com/caddy-dns/ovh
    This produces caddy.exe in the current directory - xcaddy fetches Caddy's source plus the named plugin module and compiles them together; no manual Go coding needed.
  4. Verify the plugin is present before shipping it:PowerShell
    .\caddy.exe list-modules | Select-String ovh
    Expect to see dns.providers.ovh in the output.
  5. Move the built binary into place:PowerShell
    New-Item -ItemType Directory -Force -Path C:\Tools\caddy | Out-Null
Move-Item -Force .\caddy.exe C:\Tools\caddy\caddy.exe
  6. Whenever Caddy itself needs a version bump later, repeat the build/verify/move steps with the newer Caddy/plugin versions - xcaddy build always pulls latest unless a version is pinned (e.g. xcaddy build v2.8.4 --with github.com/caddy-dns/ovh); then stop and start the Caddy service (covered next in this note) so the already-registered service picks up the new binary.

Caddyfile sample (split app/daemon, using env vars):

Caddyfile
bigdude.mydomain.cloud {
	bind 101.63.99.123
	tls {
		dns ovh {
			endpoint {$OVH_ENDPOINT}
			application_key {$OVH_APPLICATION_KEY}
			application_secret {$OVH_APPLICATION_SECRET}
			consumer_key {$OVH_CONSUMER_KEY}
		}
	}
	log {
		output file C:\Tools\caddy\logs\app.log
	}
	reverse_proxy 127.0.0.1:3110
}

bigdude-daemon.mydomain.cloud {
	bind 101.63.99.123
	tls {
		dns ovh {
			endpoint {$OVH_ENDPOINT}
			application_key {$OVH_APPLICATION_KEY}
			application_secret {$OVH_APPLICATION_SECRET}
			consumer_key {$OVH_CONSUMER_KEY}
		}
	}
	log {
		output file C:\Tools\caddy\logs\daemon.log
	}
	reverse_proxy 127.0.0.1:3010
}

Test the Caddyfile before applying it (from C:\Tools\caddy):

PowerShell
.\caddy.exe validate .\Caddyfile
.\caddy.exe fmt --overwrite .\Caddyfile

validate catches syntax/config errors without starting the server; fmt --overwrite reformats the file to Caddy's canonical style in place (useful after manual edits, and safe to run before every service restart cycle).

Registering Caddy as a Windows service

  1. Confirm the custom-built caddy.exe is at C:\Tools\caddy\caddy.exe, and the OVH environment variables are set.
  2. Register and start the service:PowerShell
    sc.exe create Caddy start= auto binPath= "C:\Tools\caddy\caddy.exe run --config C:\Tools\caddy\Caddyfile"
sc.exe start Caddy
    Stop / remove if ever needed:PowerShell
    sc.exe stop Caddy
sc.exe delete Caddy
  3. Optional: auto-restart on crash (sc.exe doesn't do this by default):PowerShell
    sc.exe failure Caddy reset= 0 actions= restart/5000
  4. Config changes need a manual restart - sc.exe-registered services can't be signaled to reload gracefully:PowerShell
    sc.exe stop Caddy
sc.exe start Caddy
  5. Firewall: scope the Windows Defender Firewall allow rule to the NetBird virtual adapter/category (set that adapter's network category to Private when Windows first prompts), not Public/Private broadly. Caddy's bind directive already prevents listening on the public adapter at all - the firewall scoping is a second, independent layer, not a substitute for it.
  6. Logs: Caddy run via sc.exe writes to stdout/stderr by default, which goes nowhere without a console attached - add an explicit log directive per site block to persist logs to a file (see the Caddyfile above), or check Event Viewer → Windows Logs → Application as a fallback.

Running caddy.exe run --config ... interactively in a terminal also shows live output for troubleshooting - but stop the service first (sc.exe stop Caddy). Caddy's own admin API binds 127.0.0.1:2019 by default, and only one Caddy process can hold that port at a time; running the interactive command while the service is still up fails with listen tcp 127.0.0.1:2019: bind: Only one usage of each socket address.... Restart the service (sc.exe start Caddy) once done debugging.

Staging vs production ACME CA: while debugging TLS issuance, Caddy's log may show requests going to acme-staging-v02.api.letsencrypt.org (Let's Encrypt's staging environment - issues untrusted test certificates, used to avoid production rate limits while troubleshooting). Once DNS-01 issuance succeeds cleanly against staging, remove/adjust any acme_ca staging override in the Caddyfile so it issues from the real production CA (acme-v02.api.letsencrypt.org) - otherwise browsers keep showing an untrusted-certificate warning indefinitely.

Why app and daemon need separate hostnames

Rule: pairing always targets the daemon hostname. In the Machines plugin, enter https://<host>-daemon.mydomain.cloud (Caddy → 127.0.0.1:3010), never the bare https://<host>.mydomain.cloud (Caddy → web app 127.0.0.1:3110). The bare hostname is for browsing only.

Device pairing (Settings → Access & network → Devices, used by the Machines plugin) calls the daemon's API (/api/devices/redeem), not the web app. If the reverse proxy points at the web app port instead, the web app answers 401 Unauthorized, and Timon surfaces this as a misleading “wrong, expired or already used” pairing-code error - even though the code itself is still valid. Tell-tale sign: the code is still shown with time remaining when the error appears, proving the request never reached the daemon.

Two situations both produce this exact misleading message:

  1. Proxy points to the web app (3110) instead of the daemon (3010).
  2. The proxy itself requires its own authentication (basic auth, Authelia, Authentik, etc.) in front of /api/* - its 401 is returned before Timon is ever reached.

Also: self-signed certs (tls internal) are rejected outright for pairing - only a real, CA-trusted certificate works (which is exactly what the DNS-01/OVH setup above provides). The “Make this machine reachable” button in Timon's UI only works with Tailscale; it's a no-op for NetBird.

Diagnostic command - from any machine, using the exact HTTPS address entered in Machines:

PowerShell
curl.exe -s -X POST https://YOUR-ADDRESS/api/devices/redeem -H "content-type: application/json" -d "{}"
ResponseMeans
{"error":"unauthorized"}The web app answered, not the daemon → fix the proxy target
A login page / proxy-branded responseThe proxy's own auth is in the way → remove auth on /api/*
{"error":"invalid_request"} or device_requires_tlsRequest reached the daemon correctly → look elsewhere

Conclusion: the web app and the daemon must be served on separate hostnames, each with its own clean reverse_proxy target - not combined on one hostname, and not split by path (fragile, risks misrouting).

Apply, use, verify, and the access-control reminder

Apply any Caddyfile change:

PowerShell
sc.exe stop Caddy
sc.exe start Caddy
  • Day-to-day browsing: https://bigdude.mydomain.cloud.
  • Pairing a new device / Machines plugin remote address: https://bigdude-daemon.mydomain.cloud (the daemon hostname, never the bare app hostname). Steps:
    1. On the machine to add (bigdude), generate a fresh pairing code: Settings → Access & network → Devices. The code must come from this machine, not from the one pairing from.
    2. On the machine pairing from, open Machines and enter the address https://bigdude-daemon.mydomain.cloud and the code.
    3. Do it right away. Generate a new code after any restart of bigdude's Timon service, and after any failed attempt.
    4. If “wrong, expired or already used” appears, run the diagnostic command from the previous section against the daemon hostname before trying a new code.

Verify:

  • curl.exe -s https://bigdude.mydomain.cloud from an enrolled remote peer - should return a redirect to /login. (Do not add -UseBasicParsing: it is a PowerShell Invoke-WebRequest parameter, and curl.exe reads it as -U, a proxy user.)
  • Confirm the hostnames are not swapped, from an enrolled remote peer:PowerShell
    curl.exe -s -D - -o NUL https://bigdude.mydomain.cloud
curl.exe -s -D - -o NUL https://bigdude-daemon.mydomain.cloud
    The bare hostname must return 307 to /login (web app). The -daemon hostname must return 401 with X-Powered-By: Express (daemon). If they are the other way round, swap the reverse_proxy targets in the Caddyfile and restart Caddy.
  • sc.exe query Caddy → RUNNING after reboot (service is start= auto).
  • Confirm both hostnames are unreachable from a device not enrolled in NetBird.
  • Confirm 127.0.0.1:3110 and 127.0.0.1:3010 both answer locally before attempting remote pairing (avoids the false “code refused” symptom caused by the app/daemon still starting up).

Access control reminder: both hostnames resolve to the same NetBird peer IP and port 443 - scope the NetBird access policy once, as set up in the previous lab note: source group timon-admins → this peer, port 443 only. No separate policy is needed per hostname, since routing between them is handled by Caddy's SNI-based site blocks, not by NetBird.

What this closes

This closes the build: a self-hosted NetBird controller on the Freebox, groups and narrow access policies instead of a flat fail-open mesh, and Timon itself reachable from anywhere over the mesh through a reverse proxy that keeps its listeners on loopback and only answers to a CA-trusted certificate. The whole chain, end to end, now mirrors the decision made at the very start of this series: self-host everything, trust the mesh explicitly, and never expose a raw port to the internet.
