Why I'm writing this down

This is the full journey, start to finish: the brainstorming that led to choosing NetBird, then the complete self-hosted setup that gets my own devices and Timon's instances reachable from anywhere. This first note covers the thinking before any install: what's on the network, what the access has to achieve, and the comparison that picked NetBird over three other options.

One honest caveat up front: I'm not a Linux expert, and not a network guru either. Some of the hardening steps later in this series will look thin to anyone who's spent a career with cables and routers. Flagged here, not hidden - I'll revisit and tighten them as I learn more.

Where this came out

OptionVerdictReason
Plain WireGuardRejectedNo control plane: O(n²) manual config, no NAT traversal, no revocation UI, fails requirement 4 (effort) past 2 devices
TailscaleRejected as primaryBest UX, but control plane is opaque third-party SaaS, fails requirements 1-3 (security/visibility/trust)
HeadscaleRejectedSelf-hostable, but an unofficial reverse-engineered clone of a closed protocol, fails requirement 3 (trust)
NetBird (self-hosted)SelectedOnly option where every component is open source and officially self-hostable, with groups/ACL/DNS built in

Ruled out first: plain WireGuard

Plain WireGuard is the most minimal, most auditable option: just the protocol, nothing else to trust. It fails requirement 4 as device count grows: every new peer needs manual key generation, manual IP allocation, and a manual [Peer] block distributed to every other peer that needs to reach it, a full mesh means O(n²) config edits. No built-in NAT traversal means per-device port-forwarding, which doesn't work at all for a phone on cellular (no fixed forwardable IP). No revocation or audit UI. Ruled out beyond a trivial two-device setup.

Best UX, wrong trust model: Tailscale

Best UX of the four, and it would win outright if "reduce effort" were the top priority. Rejected as the primary pick because requirements 1-3 (own-device security, visibility, end-to-end trust) are weakened by an opaque third-party control plane: Tailscale's servers decide route distribution and policy enforcement, and none of that can be inspected, audited, or self-run. Not a Tailscale security flaw, a conflict with the stated priority order.

Tempting, but reverse-engineered: Headscale

Solves the self-hosting gap, at the cost of running an unofficial, reverse-engineered reimplementation of a private, evolving protocol Tailscale doesn't document or guarantee compatibility for. Conflicts with requirement 3 (end-to-end trust): access control would run on a best-effort clone of someone else's closed system, not code the authors test and maintain as one stack.

The one that didn't force a trade-off: NetBird

The only option where every component, client, management server, signal server, relay, dashboard, is open source and officially designed to be self-hosted, with WireGuard underneath and a real groups/ACL/DNS model (no regression to plain WireGuard's manual-everything problem). Setup/maintenance effort is higher than Tailscale's (no managed coordination server, no one-command HTTPS publish) but much lower than plain WireGuard's (built-in NAT traversal/relay, dashboard-driven groups and policies, private DNS).

PriorityNetBird self-hosted
1. SecurityFull control over the mesh identity/access-control system
2. VisibilityEvery component is the official, inspectable implementation
3. TrustSame WireGuard crypto core, authored and tested as one stack
4. EffortHigher than Tailscale, much lower than plain WireGuard

iPhone requirement: NetBird ships an official iOS app. Sign in via the same SSO flow as any other peer and the phone becomes a normal mesh peer, with its own NetBird IP, groups, and policies. Once connected, cellular or Wi-Fi, it resolves Custom Zone hostnames (e.g. bigdude.mydomain.cloud) and reaches Timon or the hub as if on the LAN, scoped by whatever policy applies (e.g. the iphone group reaching only timon-hosts/hub, not the whole mesh).

Controller on the Freebox itself

Two placement options for the self-hosted control plane (management server, signal server, relay, dashboard):

OptionDescriptionTrade-off
(a) VM on the FreeboxUses Freebox OS's built-in VM featureHypervisor compromise could in theory affect it, same box as the internet gateway
(b) Separate machineA box behind the Freebox, which only forwards portsNo single-point-of-failure gain: Freebox down already kills internet and remote access, plus a second always-on device to buy/power/patch

Decision: (a). Since a Freebox outage already means total loss of internet and remote access regardless of where the controller runs, option (b) removes no actual point of failure, it only adds hardware with no resilience gain. The hypervisor-compromise risk was accepted because Freebox OS's VM feature is a maintained product feature, not a DIY hypervisor. Logged at the time as an accepted convenience trade-off, not an overlooked risk.
